# 开发规范

本规范适用于 AgentHub 的前端、Tauri commands、Rust 核心、CLI、测试与文档。领域术语以根目录 `CONTEXT.md` 为准，架构决策以当前有效的 ADR 为准。新代码遵守本规范；历史代码在触及相关功能时渐进治理，避免仅为改行数而整体重写。

## 设计原则（SOLID）

- **单一职责（SRP）**：一个模块只围绕一个变化原因组织。React 页面负责组合和页面状态；可复用交互放入组件或 hook，展示转换放入 `src/lib/` 纯函数。Tauri command 负责参数、权限与错误边界，文件扫描、持久化、同步和 Git 操作放入 `src-tauri/src/core/` 的对应模块。
- **开放封闭（OCP）**：新增 Agent 目录规则优先扩展 `core/tool_adapters.rs` 中的适配器定义与解析流程；新增 Skill 来源、同步方式时集中扩展对应领域入口，避免在多个页面或 command 中重复 `if/else`。只有确实存在多种稳定实现时才抽象，不为单一实现提前创建 trait。
- **里氏替换（LSP）**：同一抽象的不同实现必须保持相同的输入校验、错误语义和副作用边界。例如不同 ToolAdapter 的目录解析和扫描规则应遵守同一调用契约；不能让替换实现悄悄删除未托管文件或改变只读扫描的含义。
- **接口隔离（ISP）**：调用方只依赖所需操作。拆分过宽的 props、hook 返回值和 Rust trait；不要为一个页面注入包含扫描、安装、备份全部能力的“万能服务”。若并无多个实现，优先传入具体的小函数或值对象。
- **依赖倒置（DIP）**：领域判断不依赖 UI、Tauri 窗口或具体文件路径。前端经 `src/lib/tauri.ts` 调用 command；桌面端与 CLI 共用 `core/`。需要替换外部 I/O 以测试领域逻辑时，在边界引入小接口，而不是让核心依赖 command。

## 模块与复用边界

| 位置                         | 职责                                          |
| ---------------------------- | --------------------------------------------- |
| `src/views/`                 | 页面组合与页面级状态                          |
| `src/components/`            | 可复用展示与交互                              |
| `src/hooks/`、`src/context/` | 交互流程、订阅与共享状态                      |
| `src/lib/`                   | 纯函数与共享 bindings；`tauri.ts` 为 IPC 入口 |
| `src-tauri/src/commands/`    | 参数、权限与错误边界的薄适配                  |
| `src-tauri/src/core/`        | 扫描、部署、SQLite、同步、备份与 Git 业务     |
| `src-tauri/src/bin/`         | CLI 入口，复用 core                           |

- **KISS / YAGNI / DRY**：选择满足当前需求的最简单实现，不为假设中的功能预建框架；复用稳定的领域规则，不因代码形似就把不同业务强行合并。第三次出现相同语义的重复实现时必须抽取；安全校验与路径规则从第一次起即复用。
- 遵循 [ADR-0006](../../../../docs/adr/0006-file-size-and-reuse-conventions.md) 的拆分触发线：页面建议不超过 400 行，超过 600 行必须拆分；Rust 模块建议不超过 500 行，超过 800 行必须拆分。触及历史超大文件时优先抽出本次变更的职责，不要求一次性重构整文件。
- Agent 路径、项目作用域、文件安全校验和技能同步状态应有单一权威实现。先查现有领域类型、path guard、scanner、adapter、command 与 bindings，再新增逻辑；语义和生命周期不同才保留局部实现。
- `src-tauri/src/main.rs` 保持启动入口职责。业务规则放在 `core/`，commands 做薄适配，避免桌面与 CLI 各自实现一份。
- 公共函数与模块名称描述领域行为。Rust 遵循 `rustfmt`、`snake_case`/`UpperCamelCase`/`SCREAMING_SNAKE_CASE`；TypeScript 采用项目现有命名与格式，新增可复用逻辑应有清晰的输入、输出及错误语义。
- 页面超过 800 行禁止继续新增功能；单个函数建议不超过 50 行，超过 80 行说明不能拆分的原因。禁止复制作用域标签与诊断文案；语义或生命周期不同而保留局部实现时说明边界。

### SOLID 审查问题

- SRP：页面是否同时承担扫描、持久化或 Git 操作？将业务放回 core，展示转换放到纯函数。
- OCP：新增 Agent 或来源是否需要修改多个页面与 command？优先扩展已有适配器或领域入口。
- LSP：替换实现是否改变只读操作、错误语义或数据保护？用相同契约的行为测试验证。
- ISP：调用方是否被迫接受无关 props、操作或状态？按实际调用方缩小接口。
- DIP：核心是否依赖窗口、command 或 UI？需要隔离 I/O 时在边界注入小接口；单一实现无需机械增加 trait。

### 复用设计

- 新增实现前，查找当前调用方和同类流程，明确已有类型、组件、hook、bindings 与 core 能否承接；扩展已有入口优先于创建平行实现。
- 领域标识、安装检测、能力映射和展示转换复用权威来源。用明确的领域字段关联数据，不借用图标、显示名称或本地化文案判断身份；展示文案与业务标识分别维护职责。
- 抽取边界按业务语义、状态所有权和生命周期确定。纯转换放纯函数，交互放组件或 hook，桌面与 CLI 共用业务放 core；不要为减少几行代码增加跨层依赖、万能配置或大量布尔参数。
- 复用已有数据不等于复用所有筛选策略。例如“已安装”“已启用”“支持部署”“可启动”语义不同，应复用检测证据，并明确各入口自己的条件，不能为复用改变需求。
- 抽取或合并实现时检查所有调用方的输入、错误、顺序和副作用，迁移后删除被替代的重复实现；允许保留的差异应能说明业务原因。

## 性能与资源使用

- 按实际规模和触发频率判断成本，重点检查首屏、输入、滚动、终端输出及定时刷新路径。小型静态列表优先直接派生；没有耗时或渲染证据时，不机械添加缓存、`useMemo`、`useCallback` 或通用索引。
- React 渲染和高频事件中不发起文件扫描、IPC、网络请求或进程启动。已有 Context、hook 或后端快照能满足需求时复用结果，避免每个组件独立检测、订阅或轮询。
- 外部查询优先批量读取，避免逐行 IPC、数据库查询或进程调用。独立操作在资源允许时有界并发；存在顺序、锁或共享写入依赖的操作保持串行。
- 可能持续增长的列表、目录扫描、日志和终端输出应有分页、按需加载、虚拟化、缓冲上限或背压等适用措施；避免每次刷新全量扫描、复制或序列化全部历史。选用措施时保留搜索、排序、选择和输出完整性语义。
- 阻塞 I/O 与 CPU 密集任务放到合适的工作线程或任务边界；锁内只做必要操作，不持锁等待远端请求。定时器、监听、订阅和后台任务明确所有者，在卸载、切换作用域或退出时清理；保留需要持续运行的会话语义。
- 缓存必须说明键、作用域、失效条件、容量或有效期，以及失败后重试和手动刷新行为；合并同键并发请求，防止过期响应覆盖新状态。不能用缓存掩盖重复请求或改变身份、权限及数据新鲜度要求。
- 性能修复在可复现的场景下比较修改前后结果，记录数据规模、触发次数和相关指标，如耗时、请求数、内存或渲染次数。普通低风险改动做成本分析即可；没有测量时不得宣称性能提升，不增加易波动的耗时阈值测试。

### 审查与交付证据

- Standards 审查逐项检查职责与契约、性能与资源生命周期、复用与权威来源；Spec 审查确认优化或抽取仍保持需求行为。
- 结论指出具体调用链、重复实现或成本来源，区分必须修复的问题与可选改进。无问题时简要说明复用入口与成本判断；涉及性能修复时给出测量结果和限制，不能只写“已优化”或“已复用”。

## 前端与跨端契约

- 组件采用明确的 props 类型，外部输入先校验再使用；不以 `any`、强制类型断言或关闭 lint 绕过边界问题。UI 文案沿用 `src/i18n/`，颜色与样式遵循[视觉规范](ui-guidelines.md)。
- 状态应有唯一权威来源；可计算出的值直接派生，不维护重复状态。Effect 用于与外部系统同步，必须清理监听与订阅；异步结果避免在取消、卸载或目标切换后覆盖当前状态。
- 修改 command 名称、参数、DTO、事件或错误结构时，同步检查 Rust 注册入口、`src/lib/tauri.ts` 和调用方。数据库内部名称不等于对外契约，不为统一命名而无迁移地改动持久化字段。
- 对外采用“技能组 / Skill Group”，代码使用 `skill_group` / `SkillGroup`，数据库保留 `scenario`，CLI 使用 `skill-groups` 并兼容 `presets`、`scenarios`。用户自定义名称和存储 ID 不随本地化改写。

## 状态、错误与数据安全

- SQLite schema 变更必须新增 migration，并覆盖新库创建、旧库升级及重复执行。已经发布的 migration 不因“旧”而直接删除；只有明确最低支持版本、数据迁移与恢复策略后才能收缩兼容路径。
- 文件删除、移动、覆盖、部署前确认路径属于当前应用管理范围；沿用既有 `path_guard`、`removals` 和同步记录，不靠 UI 隐藏按钮代替后端校验。失败时保留可恢复状态，并返回能指导处理的错误。
- 不忽略会影响数据完整性的失败，不用 `unwrap` 处理正常运行时的外部输入。日志与测试 fixture 遵守仓库隐私规则，不能写入真实身份信息、令牌或带用户名的绝对路径。
- 新增设置和持久化字段应说明默认值、升级行为、用户是否可查看或修改、删除时的清理方式；避免留下没有入口可管理的隐形偏好。
- 文件系统与数据库的联合操作明确提交顺序和失败恢复；涉及共享技能库写入时复用 `repo_lock` 及现有事务边界，明确由哪一层持锁，避免重复加锁。阻塞 I/O 不占用 UI 或异步执行线程；耗时任务沿用取消和进度反馈机制。
- 源与部署目标同路径时，取消部署不能删除技能源；保留自定义技能库与 CLI 显式目录兼容性。
- 示例路径用 `~/projects/demo` 或 `<workspace>`，邮箱用 `user@example.invalid`。凭据和 Git helper 的规则见 [OAuth 与凭据维护](github-oauth-setup.md)；凭据、数据库、日志与恢复副本不得进入技能 Git 备份。

## 测试与变更范围

### 测试目录与命名

采用“单元测试就近、跨模块流程集中”的目录规则，按测试边界选择位置，不把所有测试统一搬到根目录。

| 测试类型                       | 位置与命名                                                                                                                                                                                                               |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 前端函数、Hook、组件与页面测试 | 默认与被测文件同目录，使用 `<name>.test.ts` / `<name>.test.tsx`。同一模块有多份测试需要收拢时，可放模块内的 `__tests__/`，保留 `.test` 命名并确认测试运行器能够发现。                                                    |
| Rust 模块内部测试              | 放被测模块相邻的独立测试文件，默认 `<module>/tests.rs`；按行为拆分时可用 `<module>/<behavior>_tests.rs`。实现文件仅保留 `#[cfg(test)] mod tests;` 等测试模块声明，保留平台条件与私有成员访问边界，不为测试扩大生产接口。 |
| Rust 公共接口与 CLI 集成测试   | 放 crate 根目录的 `src-tauri/tests/<behavior>.rs`，通过公共接口或进程入口验证跨模块流程。                                                                                                                                |
| 构建、版本与发布脚本测试       | 与被测脚本同目录，使用 `<name>.test.mjs`，例如 `scripts/build.test.mjs`；文档构建脚本测试放 `scripts/docs/`。                                                                                                            |
| 浏览器交互、布局与端到端验收   | 集中放 `tests/browser/`，场景入口、驱动脚本及专用 fixture 就近组织；不为同一验收另建一套根目录。                                                                                                                         |
| 前端共享测试辅助代码           | 环境模拟、渲染与编辑器等通用辅助放 `src/test/`；仅服务单个模块的辅助留在对应测试旁。                                                                                                                                     |
| 共享样例数据                   | 前端跨模块复用的数据工厂放 `tests/fixtures/`；Rust 集成测试专用数据放 `src-tauri/tests/fixtures/`，共享辅助模块使用 `src-tauri/tests/common/mod.rs`，避免被 Cargo 当作独立测试入口。                                     |

- 是否属于集成测试由调用边界决定，不以文件名或是否使用 SQLite、临时文件判定。需要访问模块私有实现的测试仍放模块内；通过公共接口验证完整流程的测试放集成测试目录。
- 测试专用辅助与 fixture 不得被生产入口导入。新增可持续维护的测试脚本时，应说明用途、前置条件和运行命令；需要自动回归的测试接入对应测试入口或 CI，不将人工验收写成自动通过。
- 现有测试随相关功能调整逐步整理，不仅为目录整齐批量迁移。

### 精简与清理

- 每项测试应覆盖明确的行为、缺陷回归或关键边界。缺陷修复必须保留能重现问题的回归测试；文档、静态文案及其他低风险可逆改动，已有检查足以验证时，不额外编写测试脚本。
- 用最少的准备代码和必要断言表达行为；只 mock 测试边界上的外部依赖，不复制被测实现，不仅检查内部调用次数、CSS 类名或源码字符串来代替行为验证。
- 同一行为优先在能可靠验证它的最低层覆盖；浏览器测试聚焦组件测试无法验证的真实焦点、布局、渲染及完整流程，不机械重复底层用例。相近场景仅在可读性更好时参数化，不为单个用例搭建通用测试框架。
- 删除已失效、无有效断言的一次性验收脚本，以及没有额外覆盖价值的重复测试；仍有关键覆盖的脚本应先保留或将该覆盖迁入现有测试。不能仅因脚本较长、未接入 CI 或缺少引用就认定其不必要。
- 删除前核对运行入口、文档引用和独有覆盖；同时清理失去用途的 fixture、辅助代码及命令引用，保留仍被测试或产品截图使用的资源，并运行受影响的验证。

### 变更验证

- 纯转换用单元测试；通过公共接口跨 command、SQLite 或文件系统边界的流程用集成测试。
- 修改前确认调用方、序列化字段、持久化数据和平台差异；删除旧分支前查引用并验证用户数据和已发布版本的兼容性。不可仅凭 `legacy`、`deprecated`、`allow(dead_code)` 或文件行数判定可删。
- 运行与改动相关的 `npm run lint`、`npm test`、`npm run build`、`cargo fmt --manifest-path src-tauri/Cargo.toml --all -- --check`、`cargo clippy --manifest-path src-tauri/Cargo.toml --all-targets -- -D warnings` 和 `cargo test --manifest-path src-tauri/Cargo.toml`；提交前检查 `git diff --check`。文档改动至少验证引用链接、格式和 tracker 状态。
- 任务状态和里程碑及时回写 GitHub Issues，用户可见行为、发布流程或兼容性变化写入 `CHANGELOG.md`。提交与审查遵循[提交规范](commit-conventions.md)。
