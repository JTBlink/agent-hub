# 定时任务本地记录规范

本规范适用于 AgentHub 管理的全部定时任务、手动运行及新建任务模板。任务定义、执行记录和业务处理状态分别管理；执行记录与业务状态仅保存在本机，不备份、不同步、不随任务导出。

## 目录与所有权

每个任务以稳定任务 ID 归属自己的任务包，显示名称只用于展示。记录统一归集到该包的 `.local/`，不写到所处理的项目，不为同一任务创建第二处记录根目录。运行器提供 `AGENT_HUB_STATE_DIR` 时使用该路径，默认是 `<任务包>/.local/state/`。

```text
<任务包>/
├── config/task.json              # 可备份：定义、日程、依赖、文件清单
├── scripts/                      # 可备份：声明的脚本
└── .local/                       # 仅本机
    ├── runs/<运行ID>/            # 平台生成：开始、结束、退出码、输出
    ├── output.log                # 平台生成：最新输出
    ├── state/
    │   ├── task-state.json       # 业务扩展状态
    │   └── .task-state.lock      # 写入期间的互斥锁
    ├── binding.json              # 本机项目绑定
    └── receipt.json              # 本机运行环境回执
```

原生任务的执行记录由统一 runner 生成，CLI `automations runs` 与 `logs --run` 读取，保留最近 100 次。Hermes 和旧任务继续从原生或已有位置读取，通过现有显式迁移流程转换；不为统一目录擅自移动历史、修改外部调度任务或复制出第二份记录。现有 Herdr 启动恢复检查点保留兼容，新增业务信息统一使用下述扩展字段。

## 扩展字段

`task-state.json` 使用独立的格式版本，不混入任务清单版本或编辑修订号：

```json
{
  "schema_version": 1,
  "extensions": {
    "mr_repair": {
      "requests": {}
    },
    "maintenance": {
      "last_check": "2026-01-01T00:00:00+00:00"
    }
  }
}
```

- 扩展名使用 `snake_case`，按业务命名；只更新自己的扩展，保留其他字段。不需要持久状态的任务不创建空文件。
- 外部对象以平台、主机、仓库和编号等稳定身份关联，不用标题或本地路径代替身份；链接、提交版本、处理状态、次数和必要验证证据保存在对应扩展中。
- 时间使用带时区的 ISO 8601。明确区分进行中、成功、失败、结果未确认及人工接管；启动成功、退出码为 0 或 Agent 空闲不代替业务成功。
- 操作前保存领取或尝试状态，完成后通过本地回调记录实际结果。次数按真实业务尝试计，不以定时器触发次数代替；新运行、脚本升级和 Agent 重启不得清零。
- 未确认的外部写入先读回核实，不重复执行。人工接管后默认停止自动处理；恢复必须显式授权，不能删除记录绕过上限。
- 不在状态中保存凭据、环境变量全量或无关个人信息；日志和证据只保留必要内容。

Python 任务复用 `automations/_shared/task-state.py` 的 `TaskState.extension(namespace)`：带任务级写锁、原子替换，并保留其他扩展。独立安装包携带 `scripts/task_state.py` 分发副本；维护源与分发内容必须一致。其他运行时实现同一文件格式与锁协议，不另建不兼容的业务状态根目录。锁冲突、格式损坏或落盘失败时停止依赖操作并保留原数据，不自动重置记录。遗留锁仅在确认无活跃写入后人工恢复。

## 备份、清理与通知

任务清单 `files` 只列可移植脚本和配置，不得声明 `.local/` 中的文件；现有包校验拒绝这些路径。任务导出及 Git 备份只读取声明内容，执行记录、扩展状态、锁、环境和本机绑定均排除。运行时状态变化不排队生成定义备份。

执行日志按统一 runner 策略清理。业务状态的保留期由任务明确声明，不随日志轮转删除累计次数或人工接管标记。删除任务沿用默认保留本地文件、显式清理本地数据的规则，不删除项目或其他任务的记录。

本地结果回调与外部通知分开：回调负责落盘业务结果；消息、桌面通知或 webhook 必须独立配置并遵循授权。未配置外部通知时，不宣称已通知人工。远端评论仅在读回验证后记录链接；通知失败不得把业务失败改写为成功，也不得清零尝试次数。

## MR 修复任务

`extensions.mr_repair.requests` 保存请求身份、链接、源提交、尝试列表和交接状态。每次修复前用 `repair_state.py --action begin` 登记，成功后才执行；验证后调用 `success` 或 `failed`，无需修复时用 `reviewed`。每个请求累计最多 3 次修复，达到失败上限转为 `manual_pending`，禁止继续修复，仍允许独立核实审查结果与人工交接。修复回调成功为 `awaiting_review`，由新的独立 run_id 重审后才可通过，修复执行者不自签通过。读回远端评论后用 `handoff` 保存证据及评论链接并转为 `manual`，后续运行跳过该请求。

修复过程中提交变化不清零计数。上次尝试停在 `running` 时，只核实该尝试结果，不重复开始修复。回调拒绝第 4 次尝试。Agent 仍须遵循回调流程；脚本不隔离或拦截 Agent 自行执行的任意命令。

审查标签与修复预算分开管理：当前 MR/PR 只使用互斥的 `ai-review::pending`、`ai-review::rejected`、`ai-review::passed`，保留其他标签，不修改关联 Issue。仅在当前版本有已确认的未处理必修问题时 rejected，证据不足为 pending，独立双轴审查通过才 passed。人工接管只记录在本地与评论，不新增评审标签。版本、执行归属、评论证据和标签均须读回核实，结果不明不盲目重试。详细写入规则由[MR 三态标签约定](../../automations/engineering/agent-mr-processing/references/review-labels.md)维护。
