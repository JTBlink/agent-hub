# agent-hub 后续规划与设计

状态：规划中。更新时间：2026-10-30。

本文集中维护后续目标、设计方向、分期和待决问题，不作为已实现功能说明。唯一设计基线是当前 Skills Manager 核心及工作台，不沿用旧 agent-hub 宿主或安装器方案。当前实现见[系统架构](../architecture/overview.md)；已经接受的架构替换决策见 [ADR-0008](../adr/0008-primary-application.md)。

## 目标与约束

以 Skills Manager 实现为基础继续开发 agent-hub，优先保持可运行、易修改和可发布。保留原 Logo、图标及深蓝、蓝青紫主题；默认应用目录为 `~/.agent-hub`。

前端、桌面端和 CLI 使用同一套工程与领域核心。不恢复旧双窗口宿主，也不为保留旧结构而复制逻辑。已有用户数据不自动迁入或清理，跨库导入需要明确设计。

## 设计方向

### 模块与目录

页面保留路由和组合；状态流程下沉到 hooks/context，共享展示规则放在 lib。Rust commands 保持边界清晰，扫描、安装、存储、同步等核心职责逐步拆分。遵循 ADR-0006，随具体功能改动拆分继承的大模块，避免一次重写全部核心。

### 技能管理与同步

沿用现有技能库、导入来源、Skill Group、工作空间部署和 Git 备份模型。按真实使用反馈改进选择、执行进度和错误反馈，直接扩展现有 core 与 CLI。项目技能库方案拟在现有安全校验和部署引擎上增加可预览的项目变更操作，不建立独立安装器。

固定应用配置、日志和 CLI 与可移动技能库分离；同步和合并继续使用现有元数据协议。重点验证库移动、备份恢复、冲突处理以及桌面与 CLI 的一致性。旧应用数据保留在原目录；当前不规划自动迁移。

#### 问题与目标

当前项目部署主要从个人技能库直接写入各 Agent 项目目录。复制模式会产生多个独立副本；符号链接可能指向个人技能库，团队成员拉取项目后无法使用相同路径。项目来源、修订和部署关系主要依赖本机状态，项目 copy 副本也不在全局 `skill_targets` 更新链路中。

目标是让团队通过项目 Git 仓库共享确定的 Skill 内容，同时保持桌面与 CLI 一致的导入、更新、部署和冲突保护。个人技能库继续负责个人收藏；项目技能库仅包含显式引入项目的技能，不恢复全局整库共享链接开关。

#### 全局与项目安装的差异

| 维度         | 全局安装                       | 项目安装                                   |
| ------------ | ------------------------------ | ------------------------------------------ |
| 使用者       | 当前用户，在本机多个项目中使用 | 项目团队，使用随仓库交付的版本             |
| 权威内容     | 个人技能库                     | 项目内技能库                               |
| 内容生命周期 | 由个人安装、更新和移除         | 随项目 Git 提交、评审、拉取和回滚          |
| 部署源       | 本机个人库，可使用绝对链接     | 项目内内容，不依赖个人库链接               |
| Agent 选择   | 当前用户的已安装工具及个人偏好 | 团队声明的支持目标；本机检测只用于诊断     |
| 更新影响     | 更新个人版本及托管的全局部署   | 显式更新项目版本，个人更新不得自动改写项目 |
| 换机使用     | 需要恢复个人库与部署           | 已提交的项目内容和入口可直接使用           |

项目安装的首要验收是：维护者安装并提交后，新成员只需拉取项目并使用团队支持的 Agent，无需安装 AgentHub、导入个人库或重新下载 Skill。来源清单服务后续维护，不应成为读取已有项目内容的前置条件。

Git 分发仍需维护者提交相关文件。应用应列出需提交的项目内容、来源清单和入口，提示当前是否被忽略；不能把“安装成功”描述为其他成员已经收到更新。

团队友好性修订（2026-10-12）：按 [ADR-0011](../adr/0011-optional-project-management.md)，AgentHub 管理清单可选共享，团队消费只依赖已提交技能及原生入口。界面分别列出技能交付和管理信息，避免将 `.agent-hub` 清单误认为必需运行文件。下方候选布局中的项目管理清单改为可选提交；来源互操作等未实现项仍保持规划状态。

#### 内容与目录

普通项目采用以下候选布局；已有目录先扫描、预览，不能因为采用该布局就直接接管。

```text
<project>/
├── .agents/skills/                 # 项目技能实际内容，提交 Git
├── skills-lock.json                # 可移植来源清单，提交 Git
├── .agent-hub/project-skills.json   # AgentHub 项目身份及部署意图，提交 Git
└── .claude/skills/                  # 默认提交可直接读取的复制副本
```

项目技能库是团队实际使用版本的权威来源。个人库或远程来源到项目库采用复制；项目库到 Agent 原生目录采用直接读取、项目内链接或复制。项目可以直接创建和编辑自有 Skill，不要求先登记到个人库。

内容及可移植元数据以项目文件为准，本机 SQLite 是索引和部署执行记录，可从项目文件重建。日志、恢复原件、操作 journal、绝对路径和凭据只留在本机，不进入项目可移植元数据。项目 Git 负责团队内容版本；应用不自动 commit、push，也不借全局备份同步改变项目内容。

已提交的 Agent 复制副本属于派生内容，但也是团队交付的一部分。通过应用更新项目库时，必须同步刷新团队托管副本；直接编辑项目库后，应用检测副本陈旧并提供刷新及完整待提交文件清单。发布过程部分失败时明确提示尚不能作为完整团队版本提交。

候选目录不是新的任意路径配置入口。路径由现有适配器与作用域解析器统一计算。链接工作空间、独立 Agent 工作空间沿用现有语义，第一期仅为普通项目增加项目技能库。

#### 来源清单和兼容性

优先读取并保留 `skills` CLI 的 `skills-lock.json`：来源、来源类型、原始 URL、ref、Skill 子路径和 `computedHash`。未知字段保留；不把损坏或未知版本的清单当作空文件覆盖。

AgentHub 专属字段放在项目元数据中，以稳定项目 Skill ID 关联来源条目、中央相对路径及团队支持的 Agent。核心与 CLI 支持为未安装的团队 Agent 生成入口；桌面项目添加按 ADR-0012 从本机已安装且已启用的 Agent 中选择。目录名、展示名和稳定身份分开处理，重命名不丢失部署关系。来源清单按名称索引，因此第一期拒绝重复来源键；通过明确重命名解决冲突。

个人 Agent 偏好、安装状态和实际执行结果只保存在本机，不写回团队声明。扫描已有项目内容不要求必须存在上述两份清单；缺少来源信息的 Skill 可正常使用和登记，来源更新能力标记为不可用或待补充。

项目元数据保存确切 Git commit、来源内容指纹、引入后内容指纹、部署意图及 schema 版本。`ref` 用于检查后续更新，commit 用于恢复选定版本。恢复下载后验证指纹，不匹配则报告失败而非静默接受最新分支。保存新版本前，确认内容指纹算法、过滤规则与外部 CLI 的 `computedHash` 兼容；不兼容的内部指纹使用独立字段，不能冒充外部字段。

个人库导入且没有可移植来源时，标记为项目内维护，团队依靠已提交内容使用该 Skill。个人路径只能作为本机可选关联。相对路径来源也需判断是否仍位于仓库内；仓库外的相对路径不视为可移植来源。

#### Agent 部署策略

| 目标情况                             | 拟议行为                                         |
| ------------------------------------ | ------------------------------------------------ |
| 适配器支持直接读取项目公共目录       | 直接使用实际内容，不生成冗余入口                 |
| Agent 采用专属目录                   | 默认从项目技能库生成受管理复制副本，并随项目提交 |
| 团队明确选择且平台支持项目内相对链接 | 从专属目录链接到项目技能库，验证检出后可用       |
| 多 Agent 解析到同一物理目录          | 一次文件操作，保留各 Agent 可见性说明            |
| 目标已有未托管内容                   | 返回冲突，允许显式接管或保持原样                 |

项目部署默认策略为“团队共享”：直接读取公共目录优先，专属目录默认复制。复制增加仓库内容体积，但避免新成员依赖链接权限或本机初始化。项目内相对链接是团队主动选择的优化项，不复用全局 `sync_mode` 默认值。Windows junction 仅作为显式选择的本机生成入口，不能当作可移植链接提交。入口复制失败与链接降级应在逐目标结果中展示实际模式。

默认提交公共内容和团队所需的专属目录副本，不将这些副本加入忽略规则，也不提交团队不需要的入口。团队可选择提交经过目标平台验证的相对链接；若选择本机生成入口，则明确提示每个成员需要初始化，这属于可选工作流，不满足默认“拉取即可使用”的验收。忽略规则仅覆盖确切托管路径，首次预览后显式应用，不能忽略整个 Agent 配置目录。已跟踪文件不由应用自动改为忽略。Windows 检出不能正确还原链接时，修复入口需识别链接文本文件并展示替换预览，不能依据文件名直接删除。

生成副本不得成为隐含的第二权威版本。记录部署时指纹，重建前读取目标实际内容；有修改则报告冲突，提供“回传项目库”“以项目库重建”“保持现状”。回传项目库也需检查其他修改，不采用时间戳较新即覆盖的规则。

#### 可见性与启停

`.agents/skills` 同时是部分 Agent 的原生发现目录。因此写入其中的 Skill 可能对所有读取该目录的宿主可见，不能只凭某个 Agent 的数据库选中状态宣称独立隔离。

界面展示“共享目录可见”及实际共享 Agent 范围。直接读取同一目录的 Agent，第一期只提供共享范围的启停，不提供虚假的逐 Agent 开关。宿主有经过验证的隔离目录或排除机制时才提供独立控制。

任何移动已跟踪内容或移除已提交入口的启停操作都属于团队项目变更，随 Git 传播，界面需明确其影响。个人禁用 Agent 不得触发对团队目录的删除、移动或入口改写；没有宿主隔离能力时，只能标记本机管理偏好，不能声称该 Agent 已无法发现项目 Skill。

项目范围停用应保留原件：候选方案是移动到项目内非发现目录 `.agents/skills-disabled`，同步记录项目级停用状态；该目录内容可随 Git 保存，需验证适配器不会将其作为技能发现根。停用公共内容前处理所有依赖该内容的托管入口，避免产生悬空链接。目录规则和外部 CLI 对停用内容的处理需在评审中确认。

#### 操作和更新语义

1. **添加到项目**：选择个人库、远程或本地来源，选择团队支持的 Agent，预览名称、可见范围、冲突及文件变更，再将内容引入项目库并生成团队入口。结果列出需提交文件，不以本机 Agent 安装状态限制目标。
2. **部署到 Agent**：以项目库已有内容生成入口；不下载来源、不改变选定版本。
3. **检查来源更新**：比较来源新版本与引入基线；不覆盖项目内容。全局技能更新仅使关联项目出现可更新提示。
4. **更新项目版本**：同时比较引入基线、项目当前内容和来源候选内容。项目未修改时预览后更新；双方修改则返回冲突。第一期只做比较和明确选择，不自动文本合并。
5. **恢复内容**：内容缺失时按固定修订恢复并验证指纹；没有可移植来源时引导从项目 Git 恢复。
6. **刷新部署入口**：按当前项目内容修复缺失、陈旧或不可用入口，不把“修复”解释为升级来源版本。

团队维护流程为“添加或更新 → 刷新所有团队托管入口 → 查看项目 diff → 提交并评审”。成员消费流程为“clone/pull → Agent 直接读取项目文件”；使用已有内容无需访问来源。AgentHub 在 Git pull 后只重建本机索引并报告异常，不以旧本机状态覆盖仓库内容。项目版本回滚后，内容、入口和清单应一同回到该提交。

引入基线至少保存可信内容指纹。第一期通过两侧指纹判定修改，通过项目与来源 diff 展示候选；缺少基线时标为未知并要求预览，不能推断项目未修改。真正的三方合并需要保存基线内容，留待后续设计。

来源检查、项目修改和部署健康分别展示，避免混用一个“同步状态”。时间戳只作辅助展示，内容一致性以实时指纹为准。

#### 模块与安全执行

建立职责明确的项目技能管理 core 模块，桌面 commands 和 CLI 都通过同一接口执行。对外接口围绕扫描状态、预览操作和应用操作组织；预览不是永久覆盖授权，应用时必须复查文件状态。

内部复用既有适配器、扫描器、路径保护、安装复制规则、删除预览和部署引擎；全局与项目保留各自的状态生命周期。入口不再重复拼路径、删除目录和写来源信息。新模型不能把项目部署硬塞进仅按 Skill/Tool 唯一的全局目标表；索引应明确项目作用域。

项目操作按真实根目录串行化，覆盖扫描、检查和发布；若同时写个人库，复用 RepoLock 并规定唯一锁顺序。网络下载在写锁外完成，进入锁后重新读取当前状态。锁只能约束应用实例，外部进程的变化仍需指纹复查。

文件写入采用 staged、保留原件和 journal。以项目实际内容及元数据的发布为提交点，数据库随后重建；多文件发布中断由 journal 恢复，不能假定单次目录 rename 覆盖所有状态。中央内容发布成功但部分入口失败时返回“内容已更新、部署部分失败”，保留原件及可重试记录，不笼统返回成功或假称全部回滚。

普通替换与删除检查目标归属、部署指纹和当前类型；应用旧记录不构成任意覆盖授权。预览被外部编辑改变时停止受影响操作并重新预览。删除项目记录、卸载入口和删除项目实际内容必须是不同意图；关闭 Agent 不删除唯一项目内容。

#### 已有项目迁移

迁移为用户显式操作，不在启动或扫描时自动执行。

- 扫描公共目录、Agent 原生目录及停用目录，识别同内容副本、分歧副本、链接和未托管目录。
- 内容一致的条目可归并；同名不同内容逐项处理，未选择的版本保留。
- 指向个人中央库的链接先读取实际内容并复制到 staged，发布成功后才重建入口。
- 缺失来源或悬空链接列为不可恢复项，不生成空 Skill。
- 已有 `.agents/skills` 可能已有团队自有内容，原地登记优先，不清空目录、不强制改名。
- 提供迁移前后路径与 Git 变更预览，保存可恢复原件；中断后可恢复或继续执行。

该方案改变了既有项目“各 Agent 副本”和停用目录的语义。实施前需增加项目技能库 ADR，并明确与 ADR-0009、已有项目启停规格的关系；草案阶段不修改已接受决策或将新语义写成当前实现。

#### 实施分期

| 阶段               | 范围                                                                                 | 完成依据                                                              |
| ------------------ | ------------------------------------------------------------------------------------ | --------------------------------------------------------------------- |
| P0：现有安全问题   | 覆盖安装保留身份及关联；删除前路径校验；逐目标错误可见                               | 同路径来源、关联保留、部分失败回归通过                                |

#### 验收与测试

优先通过项目技能管理 core 的公共行为验证，沿用现有临时目录、SQLite 和本地 Git fixture，不操作真实个人技能库。

- 维护者提交项目文件后，新成员 clone 到全新目录，无 AgentHub、本机数据库、个人库和网络访问，仅用团队支持的 Agent 即可读取已提交 Skill；至少覆盖公共目录直接读取和专属目录副本两类目标。
- 维护者本机未安装某个团队目标 Agent，仍可生成并提交其入口；个人禁用 Agent 不改变团队项目文件。
- Git pull 和项目回滚后公共内容与团队副本一致；缺少来源清单不阻止读取已有项目内容。
- 安装结果显示公共内容或团队入口被 Git 忽略、入口部分失败及待提交文件，不将本机安装成功误报为团队同步完成。
- 项目移动、Git worktree 换路径后，相对链接有效，绝对 junction 可识别并修复。
- 项目未修改且来源更新时，只更新所选 Skill；其他技能及关联保持完整。
- 项目或部署副本有修改时，常规更新、重建和取消部署不能静默销毁这些修改。
- 固定修订恢复验证内容指纹；ref 前移不改变恢复版本。
- 来源丢失、权限失败、数据库失败和阶段间进程中断均返回可观察状态，原内容可恢复。
- 共享物理目录只执行一次写入；取消一个入口不破坏其他仍在使用的入口。
- Git pull 后索引可重建，不以本机缓存反向覆盖项目清单；损坏清单和未知版本停止写入。
- 未托管内容、嵌套路径、源目标重叠、链接逃逸和预览后修改均有拒绝覆盖的行为测试。
- 三语界面区分来源更新、项目修改和入口健康，展示真实共享可见范围及逐目标失败。

实现时运行相关前端检查、Rust 测试、格式及 Clippy；平台链接行为需原生系统验证，不能只以单平台单元测试代替。

#### 待评审项与非目标

已确认方向：项目安装服务团队共用；项目 Git 分发实际内容；公共目录直接读取，专属目录默认提交复制副本；个人库和本机 Agent 偏好不改变团队版本。

待评审：来源清单与项目元数据的双文件布局、停用内容目录、可选链接的目标平台范围，以及第一期是否必须支持外部 `skills` CLI 写回后的完整互操作。前述兼容字段是目标，尚未承诺格式完全兼容。

第一期不包含自动三方合并、自动提交或推送项目、团队权限与审批系统、新建远程技能注册中心、全局整库共享链接，以及对不支持隔离的 Agent 强行实现独立禁用。

### 定时任务独立包与安装生命周期

状态：已接受，核心实现已落地（2026-10-30）；执行与验证记录见 [#222](https://github.com/JTBlink/agent-hub/issues/222)。实现覆盖独立包、模板调整、安装卸载、导入导出、更新恢复与旧任务迁移。当前行为以[自动化架构](../architecture/automation.md)和 [ADR-0016](../adr/0016-independent-automation-packages.md) 为准；下文保留设计基线，平台原生验收按实际记录确认。

#### 现状与调整范围

现有 `core::automation` 已有原生调度与 Hermes 适配、独立默认脚本目录、执行记录、删除清理和失败重试。缺口在于完整定义及删除状态集中存放于 `tasks.json`，单个文件损坏会影响全部托管任务；显式脚本目录可以共用；模板的 `setup.sh` 尚未纳入统一生命周期，删除任务不能自动撤销安装资源。

保留 GUI / CLI 共用 Rust core 和系统调度器，不增加依赖桌面常驻的调度进程。将管理单位从“全局记录加若干脚本”调整为“独立任务包加本机安装回执”。独立包括定义、脚本、依赖环境、运行记录、锁和安装状态；任务仍以当前用户身份运行，目录隔离不代表操作系统沙箱。

#### 一任务一目录

新任务使用以下布局，沿用已有按名称安全分配、冲突追加后缀、改名不搬目录的规则；唯一身份使用稳定实例 UUID，不从目录名推断归属：

```text
~/.agent-hub/automations/<allocated-task-name>/
├── task.json                 # schema、实例 ID、名称、日程、入口、依赖声明
├── scripts/                  # 本任务脚本及资源
├── prompt.md                 # Agent 任务的提示词（存在时以正文为准）
├── README.md                 # 用途、运行条件、安装与清理说明
└── .local/                   # 本机私有数据，不进入导出和 Git 备份
    ├── binding.json          # 本机项目工作目录、凭据引用等绑定
    ├── receipt.json          # 实际调度标识、依赖及资源归属
    ├── operation.json        # 当前安装／升级／卸载阶段及恢复信息
    ├── operation.lock        # 本任务生命周期锁
    ├── env/                  # 本任务专属依赖环境
    ├── state/                # 检查点、去重标记等持久运行状态
    └── runs/<run-id>/        # 每次执行的状态、标准输出及错误输出
```

`AGENT_HUB_AUTOMATION_HOME` 的隔离约定保留；包目录统一经 `workspace` 解析，不能由调用方重复拼接。`workdir` 只表示执行目录；选择同一个项目的两个任务仍分别拥有上述目录。新托管包不提供共用脚本目录选项；复用模板采用复制内容，依赖已有脚本采用显式外部引用，引用目标不纳入卸载范围。旧自定义或共享脚本目录按兼容规则继续读取。

`task.json` 保存可移植意图，`binding.json` 保存本机路径和凭据引用，`receipt.json` 保存实际安装结果；三者不能互相覆盖职责。脚本和 `prompt.md` 为正文的唯一来源，清单只保存相对入口和内容指纹，不再在 `draft.files` 中长期保存另一份权威正文。外部编辑通过内容指纹使现有 `revision` 失效，保存时复查。

系统应用数据目录保留轻量索引：任务 ID、已登记包位置及扫描错误。索引可从受管理根目录和显式登记位置重建，不保存唯一任务定义或唯一卸载状态；只扫描已知位置。单包损坏只影响该任务，其余任务仍能展示、编辑和执行。系统调度配置必须放在操作系统规定位置，由回执逐项记录。

导出任务包时去掉实例 ID、全部 `.local` 和凭据，重新安装生成新实例身份；同机维护原实例通过显式更新完成。备份仅同步清单、脚本、提示词及说明；恢复得到未安装任务，补齐本机绑定后才能注册调度。复制原始目录导致重复实例 ID 时报告冲突，不自动加载第二份。

#### 小接口与内部职责

GUI 与 CLI 共用 `inspect`、`install`、`update`、`uninstall`、`run`；暂停和恢复仍走现有日程编辑能力。安装调用返回任务 ID、安装状态和逐项结果，后台进度和恢复状态均能重新查询；模板创建与本地导入调用同一安装流程。以下为目标模块划分，实施时复用已有实现：

| 模块 | 职责与已有代码的关系 |
| --- | --- |
| `package` | 清单版本、文件指纹、导入导出；由 `definition` 与模板内容处理抽取 |
| `workspace` | 包路径、实例身份和目录归属，复用现有路径保护 |
| `lifecycle` | 安装、更新、卸载的阶段编排与恢复，从 `managed` 抽取 |
| `dependencies` | 探测依赖、准备独立环境、记录安装归属与验证结果 |
| `store` | 单任务原子记录、操作日志与锁；全局文件仅作索引 |
| `native` / `hermes_manage` | 调度注册、撤销、查询和触发，复用实际存在的适配器 |
| `local_data` | 按安装回执清理，继续保护项目、自定义路径与共享资源 |

普通编辑继续复用现有 IPC / CLI 输入，经 core 转为包更新；不要求前端自行完成文件写入、依赖安装或系统命令调用。任务执行统一经过运行入口检查安装状态，只有完整安装且未处于更新或卸载中的任务可以执行。

#### 自动安装与依赖管理

安装是一项操作内完成的流程：校验包及本机绑定 → 在受管理目录准备内容 → 检查依赖 → 安装任务私有依赖 → 验证入口 → 以暂停状态注册调度 → 持久化安装回执 → 按用户选择启用。安装不执行任务正文。调度器不支持原生暂停创建时，适配器必须用无触发器注册或安装状态门控保证未完成前不启动。

每个写入或注册步骤前先记录可恢复意图，成功后记录实际结果，最后提交安装状态；记录失败时不得继续启用。失败可撤销的资源按回执逆序清理；撤销失败保留可重试的 `install_failed` 及具体步骤。单纯创建草稿不下载依赖，用户执行“安装”后自动完成全部普通步骤。

第一期只支持实际使用的依赖类型：任务私有 Python 虚拟环境和内置模板所需外部命令。依赖声明包含版本约束及适用平台；Python 包使用任务自己的环境和确定版本，不改全局 Python。已有外部工具只探测和绑定，不记为本任务所有；缺少且无受支持安装方式时返回明确缺项，不使用任意网络脚本猜测安装。Node 环境与共享下载缓存按真实任务需要后续扩展。

安装回执逐项区分 `created`、`reused` 与 `external`，保存资源类型、实际位置、校验信息和释放方式。新建私有环境可随任务卸载；已有 Hermes、Herdr、Git、解释器、技能库、模型配置及凭据不被自动移除。凭据使用现有凭据机制或显式本机绑定，不进入清单与安装日志。

首期不自动执行导入包中的任意 `install.sh` / `uninstall.sh`。内置网络重置模板的管理员资源可通过受支持的专用安装动作接入，清楚展示其确切操作，完成已有权限流程后写入回执；无权限时任务保持“待完成安装”，不能报成功。卸载该资源同样执行专用动作；旧模板没有可靠回执时不得按固定文件名认领管理员资源。

#### 自动卸载与数据保留

“卸载”先停止新的计划触发，确认任务未运行，再依据回执撤销该任务的系统注册、Hermes 桥接文件和私有依赖。默认保留定义、用户脚本、提示词、运行产物及历史，任务变为“未安装”，可再次安装。执行中的任务沿用现有规则，提示运行结束后重试；不自动强杀进程。

“删除任务”先完成卸载，再按现有“同时删除本地任务数据”选项决定是否删除完整包。项目工作目录、外部脚本、其他任务引用的目录、预先存在的工具与无归属证据的资源始终保留。由某任务创建后又被其他任务引用的资源也必须保留并显示原因，不能只凭最初创建者删除。清理前和实际删除前复核归属、路径及链接，复用当前 `local_data` 的保护规则。

卸载状态采用 `uninstalling` → `uninstalled`，失败为 `uninstall_failed`；安装使用 `installing` → `installed`，失败为 `install_failed`。阶段信息与最后一次错误持久保存，重试跳过已完成步骤，文件不存在视为已完成；调度撤销失败时不删除仍在使用的入口和环境。安装状态与日程启停、最近运行结果分别展示。

最终删除包前，在内部应用数据目录写入最小删除 journal，删除成功后清理索引和 journal；此记录只负责完成最后一步，不承载长期任务定义。这样包目录已删除但索引提交失败时仍可重试。记录和阶段提交使用原子替换；不能把跨文件系统和调度器的操作描述为单次原子事务。

#### 并发、更新与 Hermes 兼容

长操作持有任务锁，不持有全局索引锁；不同任务可独立安装、卸载和查询。索引锁只用于短时提交。相同任务在 GUI、CLI 及恢复流程之间串行，安装状态检查与运行领取共用门控；启停调度与运行入口之间发生竞争时，更新或卸载中的任务不进入正文。生命周期操作应能感知操作前已经领取的运行。

更新在任务自己的暂存目录准备候选，保留当前已安装版本可用。切换前禁止新运行、等待当前运行结束并核对版本指纹，依次切换包内容和调度配置，再提交回执；失败尝试恢复旧入口、旧环境和旧调度。无法完全恢复时显示 `update_failed`、禁止继续触发并保留两个版本的恢复信息；用户修改过的脚本不能静默覆盖。

系统任务继续使用 launchd / systemd timer / Windows 任务计划程序。新建 Hermes Agent 任务继续遵循现有 Herdr 执行方案；已有或明确选择 Hermes 原生调度的任务经原生 CLI 管理，不直接写 `jobs.json`。Hermes 自己仍可能集中保存其定义，AgentHub 的独立包不能消除这个外部限制。

如 Hermes 原生任务需要 `script` / `monitor_script`，在已核实 profile 的 `<HERMES_HOME>/scripts/agent-hub-<instance-id>/` 下复制最小桥接文件；不使用指向包外的软链接规避 Hermes 路径检查。先核实已安装 CLI 支持相应参数，不支持时返回能力缺项，不编辑原生定义文件替代。桥接文件及 Hermes ID、profile、配置位置写入回执，卸载只处理确切匹配项，保留其他 Hermes 任务和 profile 数据。

#### 兼容迁移与实施顺序

存储决策已记录于 ADR-0016，范围登记于 GitHub Issue #222；实现交付不自动迁移本机已有任务。读取旧 `tasks.json`、UUID 目录、名称分配记录和自定义目录的能力保留，兼容期明确区分旧记录和新包的权威来源，禁止双写两套定义。

迁移为显式维护操作：暂停并确认空闲 → 校验源指纹 → 复制候选包及必要运行状态 → 验证入口和本机绑定 → 切换调度目标 → 提交新回执及已迁移标记。旧记录标记后不再参与旧 runner 自动升级。任一步失败保留旧内容和恢复信息；共享脚本目录只复制本任务已确认的文件，不搬走整个目录，旧管理员资源保留外部归属。迁移及离线索引重建都不能触发正文或无条件启用计划。

| 阶段 | 范围 | 完成依据 |
| --- | --- | --- |
| P1 | 独立包、单任务持久化与锁、原生安装／卸载、索引重建 | 两个任务独立管理；损坏一个包不阻断另一个；安装失败无活跃调度 |
| P2 | Python 私有环境、依赖回执、内置安装动作、详情与 CLI 入口 | 一次安装完成准备；卸载清理自有资源；失败步骤可重试 |
| P3 | 旧任务迁移、更新回滚、备份恢复与 Hermes 原生桥接 | 旧项目和脚本不丢失；恢复默认未安装；跨调度器归属不混淆 |

完整交付包含 P1–P3；各阶段单独验证，不将仅拆分文件当作生命周期已完成。实现期间同步当前架构、三语界面、内置 CLI Skill 和用户可见 CHANGELOG。

验收通过 core 公共接口及临时目录、模拟调度适配器开展，避免安装或卸载真实个人任务：两个同名且同工作目录的任务互不覆盖；单包／索引损坏可隔离或重建；跨进程同任务互斥且不同任务不被长安装阻塞；每个阶段中断均可恢复；注册失败、启用失败、回执写入失败、管理员权限失败和清理失败均返回真实状态；同一任务重复安装／卸载无重复注册；更新失败保留原版本及用户修改；卸载不移除共享资源、项目目录、外部链接目标和凭据；运行与卸载竞争时无新正文启动；旧版迁移可回退；备份恢复不自动执行。三种系统调度器分别进行原生验收，单平台测试不代替跨平台结果。

### 发现：Skills 与自动化任务

实现记录：[发现页](https://github.com/JTBlink/agent-hub/issues/224)。侧栏与页面统一命名「发现」，一级为 `Skills | 自动化任务`，二级选择安装来源。保持原推荐 Skill 卡片的 `p-3`、13px 标题、12px 描述和紧凑网格；不采用早期原型中的大卡片。

| 类型 | 来源 | 安装后管理位置 |
| --- | --- | --- |
| Skills | 推荐、浏览榜单、本地安装、Git 安装 | 技能库及 Agent 工作空间 |
| 自动化任务 | 内置推荐、本地目录／JSON、Git 安装 | 自动化：查看、运行、启停日程与卸载 |

`/discover` 为新入口，旧 `/install?tab=...` 继续兼容。两个类型独立保存来源和搜索／表单状态；自动化支持 `type=automations&source=local` 直达。第一层 Tab 支持方向键、Home/End 和可见焦点，切换类型不会重建 Skills 状态。

安装统一为「任务预览 → 本机配置 → 安装结果」。预览展示用途、默认日程、声明依赖、脚本与提示词内容；本机配置包含实例名称、项目与日程，脚本目录由系统分配。准备声明依赖并注册后默认暂停，不立即运行。成功后前往自动化管理；同一来源可独立安装多个实例。

创建实例与安装分阶段提交；安装失败保留实例和错误，重试继续安装原实例，不能重复创建。已经创建的实例配置锁定，可进入任务详情维护。读取来源、文件选择或模板失败不会创建实例；切换来源后的过期异步结果不能覆盖当前页面。

Git 复用既有 URL 解析、代理、凭据和隔离 checkout。识别单任务根目录或 `automations/` 子树中的 `task.json`，固定 HEAD commit，返回已校验的内容快照后清理 checkout；安装不重新获取浮动分支。扫描限制深度、条目数、任务数和返回体积，不跟随链接；损坏单包返回独立错误，可继续安装其他有效包。分支或标签可选，目录 URL 继续沿用既有解析规则。分发仓库约定：

```text
repository/
├── skills/
│   └── development/example-skill/SKILL.md
└── automations/
    └── development/daily-project-review/
        ├── task.json
        ├── README.md
        ├── prompt.md       # 智能体任务按需提供
        ├── herdr.json      # Herdr 配置按需提供
        └── scripts/
            ├── run.sh      # 按目标平台提供入口
            └── agent.py
```

`task.json` 复用 ADR-0016 的唯一清单，README 提供说明，不增加 AUTOMATION.md 或任意安装／卸载脚本钩子。分发包不携带本机路径、实例身份、凭据、日志或 `.local/`。内置模板使用嵌入目录及本地化元数据，由模板 API 生成可安装 draft；外部分发使用导出的 JSON 或符合独立任务包 schema 的目录，不能将内置模板元数据文件直接作为便携包。

安装实例位于 `~/.agent-hub/automations/<allocated-name>/`，每个实例具有独立的 `.local/binding.json`、`receipt.json`、`env/`、`state/`、`runs/`；更新恢复时按需生成 `operation.json`。既有卸载和资源归属保护继续由 Rust core 实现。自动化来源卡片表示可重复安装的定义，实例状态在自动化页查看，不按名称推断已安装状态。

页面壳 `Discover` 负责分类与来源导航，既有 Skills 面板保持原流程；自动化来源、紧凑卡片和安装向导独立组件化。日程输入和展示格式与已有编辑器共用。界面验收使用 `tests/browser/product-preview.tsx` 中的生产组件与合成数据，以生产组件和当前需求为准。
