# 基于 Cargo features 的标准版与定制版设计草案

日期：2026-11-05。状态：首期已实现，验证记录见执行规格。本方案替代此前的三类产品草案，执行规格与验证见 GitHub Issue #289。标准版为 `standard`，首期个人版示例为 `personal`；源码非公开仍属于定制产品的存放策略。后续规划与当前实现分别阅读本方案和应用组装架构。

## 术语与产品关系

采用 Rust 官方术语描述编译机制，产品概念与编译概念分别命名：

| 名称                       | 含义与命名约定                                                                     |
| -------------------------- | ---------------------------------------------------------------------------------- |
| Cargo feature（功能特性）  | 一个可选编译能力，例如 `terminal`、`herdr`、`automation`；Cargo 中以短横线连接多词 |
| Feature set（特性集合）    | 一次构建实际启用的 features 及其传递依赖，不是额外的 Cargo 配置语法                |
| Feature module（功能模块） | 拥有自身侧栏、页面与业务实现的模块；前端沿用 `src/features/<name>/`                |
| Product config（产品配置） | 本项目定义的组装输入，选择特性集合、侧栏顺序及发行身份；不是 Cargo 内置概念        |
| Build profile（构建配置）  | Cargo 的 `dev`、`release` 等优化、调试设置，独立于产品选择                         |

只保留两类产品：**标准版**和**定制版**。此前所谓“私有版”并入定制版；源码是否公开是存放和访问策略，不产生第三类产品，也不表示收费等级。多个交付对象对应多个定制产品配置，彼此不继承整个可执行应用。

```text
共享实现 + 标准产品配置 --------------------> 标准版
共享实现 + 所需功能模块 + 定制产品配置 ------> 各定制版
```

不同产品通过编译时组装生成安装包。产品内部只有一套 Tauri 宿主和公共生命周期；不提供运行时产品切换或动态扩展安装机制。Cargo features 只表达可累加能力，不定义互斥的产品身份。

## 目标与裁剪范围

每个新增功能独立维护侧栏模块，并可按产品需要整体排除。产品未选择的功能，其专属 Rust 模块、IPC、状态、启动逻辑、前端页面、侧栏、快捷键、资源和打包程序均不进入该产品的构建结果。被其他已选功能依赖的公共代码仍保留。

“没有入口”不等于“没有编译”。验收同时检查 Rust 依赖图、前端构建图、IPC 行为和安装包内容。专属依赖不能通过另一个公共聚合入口被重新引入；完整源码 checkout 和锁文件含有未启用依赖，不等于它们已被编译或打包。

## 功能模块与侧栏接口

公共工作台提供一个组装 seam：模块声明侧栏贡献和路由，工作台负责统一布局、选中状态、展开收起、尺寸、焦点和可访问性。模块内部维护业务状态、数据查询和资源生命周期，公共侧栏不接收所有功能的专属参数。

候选最小 interface 如下，实施时根据首个迁移模块的调用方确定最终类型：

```tsx
type SidebarContribution =
  | {
      kind: "panel";
      id: string;
      labelKey: string;
      icon: ComponentType;
      component: ComponentType;
    }
  | {
      kind: "link";
      id: string;
      labelKey: string;
      icon: ComponentType;
      to: string;
    };

interface FeatureModule {
  id: string;
  sidebar?: SidebarContribution;
  routes?: readonly RouteObject[];
}
```

`src/features/<name>/module.tsx` 是模块对工作台的组装入口。复杂面板通过内部 adapter 接入公共项目、终端等能力，不把私有状态暴露给侧栏容器。跨功能动作放在同时依赖双方的集成模块中。例如 Herdr 与任务的联动可由 `tasks-herdr` 集成负责，普通任务查询不因使用任务功能而强制编译 Herdr。

产品配置显式指定上下区域的模块顺序及默认面板。组装时校验重复模块、贡献 ID、路由冲突、未启用模块引用和无效默认面板。路由激活、命令面板、快捷键及页面恢复均消费同一组装结果；恢复到已排除功能时返回有效默认页面，不触发其旧监听或任务。

先迁移真实需要的侧栏、路由和动作，不预建任意 slot 或通用扩展 SDK。设置页、菜单等贡献在实际迁移触及它们时补充。

## 产品配置与构建入口

候选目录为 `products/standard.json`，非公开定制配置保存在各定制仓库的对应目录。产品配置示意：

```json
{
  "id": "personal",
  "features": ["projects", "terminal", "herdr"],
  "sidebar": {
    "primary": ["projects", "herdr"],
    "bottom": ["settings"],
    "defaultPanel": "projects"
  }
}
```

示例只说明结构，实际公共基础模块及 feature 清单在第一阶段清点后确定。模块目录声明前端入口、对应 Cargo feature、必要权限与资源；产品配置只选择模块，不复制依赖规则。依赖关系以 Cargo feature 图为准，构建工具解析后计算实际特性集合，再生成前端装配，避免维护两套依赖图。公共基础壳和无前端贡献的依赖分别明确标记。

在现有 `scripts/app/` 入口增加产品选择，候选用法为 `npm run app:build -- --product standard`。同一解析结果驱动桌面 Rust、配套 CLI、前端入口、权限和资源清单；现有默认命令继续构建标准版。不能只给最终 Tauri 命令传参而遗漏当前 `prepareCli` 和前置前端构建。

构建时拒绝未知特性、无效组合及前后端不一致。应用公开只读构建信息，记录产品 ID、实际 features、基础提交和配置摘要；前端启动时核验摘要，错配即报告构建错误。生成结果可重建，不作为第二份手工维护的配置。

按产品与配置摘要隔离前端输出、类型检查缓存、CLI staging 和打包目录，防止连续或并发构建混用资源。Cargo 缓存可复用，但不能把同一输出位置最后生成的 CLI 当作所有产品的配套程序。

## Rust 编译时组合

先在现有 crate 中建立 features，不为目录形式一次性拆出所有 crate。以下是候选示例，不代表当前 Cargo.toml 已支持：

```toml
[features]
default = ["standard"]
standard = ["projects", "terminal", "herdr", "automation"]
projects = []
terminal = ["projects"]
herdr = ["terminal"]
automation = []
```

`standard` 是保留默认开发行为的能力集合；最终应覆盖现有完整功能。产品构建统一使用 `--no-default-features` 加显式特性集合，下游对共享库依赖也设置 `default-features = false`。`standard` 不是产品身份，不能通过它识别数据目录或更新来源。

```rust
#[cfg(feature = "herdr")]
pub mod herdr;
```

专属第三方依赖设为 `optional = true`，由 `dep:<dependency>` 关联；公共依赖按实际调用保留。使用 `#[cfg]` 排除模块及引用，不以 `if cfg!(...)` 代替。core、commands、状态初始化、启动与退出、CLI 子命令、测试入口都应成套处理。

既有 IPC 保持命令名和可信 WebView 校验。第一阶段用最小编译验证确定现有 Tauri handler 的条件组合方式，不假设宏接受任意条件条目；只有一次公共 handler 组装。新增独立定制能力可按 feature 注册 Tauri 插件，插件自行处理命令权限和调用者校验。不得通过后续 `setup` 或 `invoke_handler` 覆盖公共处理器。

功能规模、依赖隔离或多个消费者确有需要时，再迁为 workspace 中的可选 crate。Cargo 构建选定宿主包及其依赖，不用 `--workspace` 构建证明产品排除了其他成员。保持项目声明的 Rust 最低版本兼容，不因模板引入更高版本 resolver 或语法。

## 前端编译时组合

为所选产品生成只导入已启用功能的静态入口，通过 Vite alias 指向该入口。公共代码不能静态导入所有模块再按布尔值过滤，也不使用包含全部模块的动态 import 表。已启用页面可继续懒加载；懒加载本身不能排除功能代码。

同样裁剪模块专属样式、i18n、帮助内容、自动化模板及资源，避免全量 glob、聚合导出和资源复制绕过选择。外部工具的通用协议兼容与内置集成分别判断：移除 Herdr 内置集成不应擅自删除既有任务包或用户文件。

当前 `tsconfig.app.json` 全量包含 `src` 和原型。产品构建应生成以公共入口及已选模块为根的类型检查配置，排除原型和未选功能；`exclude` 不能阻止已被 import 的文件重新进入检查图。全源码质量检查保留为独立开发／CI 检查，不作为产品编译入口。未选的模块不参与产品构建和前端打包。

| 位置                                                  | 已核实情况与候选改造                                               |
| ----------------------------------------------------- | ------------------------------------------------------------------ |

| `Sidebar.tsx`、`sidebarSections`                      | 直接管理各面板和搜索快捷键，专属逻辑回到模块；默认值从产品配置派生 |

| `src/lib/tauri.ts`                                    | 聚合导出 Herdr bindings，清理公共路径对可选模块的反向引用          |
| `desktop/mod.rs`、`startup.rs`、`ipc.rs`              | 直接注册功能状态、启动与命令，按 feature 成套装配                  |

## 仓库归属、兼容与发行身份

标准版及共享能力在公开仓库维护。定制版以薄入口、产品配置和专属模块复用共享实现；非公开代码保留在定制仓库，不提交到公开仓库再靠 feature 隐藏。公开标准构建不需要任何非公开依赖或凭据，连依赖解析也必须独立完成。

首个独立定制仓库可固定共享仓库 checkout，让 Rust 与前端依赖同一提交；前端明确包入口、资源和依赖解析仍需实施，当前不能直接当成已发布 UI 包。React、Router、Provider、主题和公共业务保持单一实现。后续共享定制模块只有在实际复用时抽包，不建立单独“私有版”层。

标准版保留现有 `VERSION`、数据目录、IPC 和默认行为。独立安装的定制版采用自身产品身份、版本、数据命名空间、keyring service、CLI 路径、更新来源及签名配置，身份在数据库初始化前生效；不能在 `builder()` 返回后再切换路径。相同产品的特性集合变化不自动改变其身份。

关闭 feature 不删除用户数据，不移除或重排已经发布的公共数据库 migration，也不重置定时任务运行记录和累计状态。重新启用后按原兼容约定读取；定制私有数据使用独立存储或明确命名的迁移。项目内既有 `.agent-hub` 协议不因产品名称不同而改写。

同一应用身份的功能缩减升级必须提示不再提供的入口。后台已有系统任务、外部进程和任务包不因模块未编译就被自动停止、删除或迁移。可独立安装的定制产品默认不共享可写数据库，显式内容导入与既有项目共享沿现有修订、锁和冲突规则执行。

## 实施顺序与验收条件

1. 清点最小公共壳与实际功能依赖，建立产品配置解析和构建信息；标准配置先保持当前行为。
2. 以 Herdr 为首个纵向切片，迁移其独立侧栏及所有前后端引用，完成含 Herdr／不含 Herdr 两种构建。普通终端与任务查询在后者仍可用。
3. 接通统一构建：桌面、CLI、前端类型检查、静态入口、权限和资源；连续构建不同配置时验证产物不串用。
4. 逐个迁移自动化、预览等需要选择的功能，每次都覆盖启用与关闭行为，再按实际规模决定是否拆 crate。
5. 首个真实定制产品出现时补齐独立身份、存储与更新验收；此前只提供公共样例，不预建无交付对象的仓库。

验收矩阵至少包含标准完整集合、最小可运行集合、无 Herdr 且保留普通终端／任务的集合，以及实际交付的各产品配置。对支持的集合分别运行前后端构建、格式、Clippy 和适用测试；全特性测试不能代替关闭特性的测试。非法组合须给出明确错误。

验证未启用功能不在 Rust feature／依赖图、Vite 构建模块及资源清单中；若依赖仍由其他功能使用，记录其保留原因。调用未注册 IPC 应失败，侧栏、快捷键、深链接和页面恢复不会进入缺失功能。检查 CLI 帮助、配套程序身份、安装包内容与插件权限，不能仅凭二进制字符串搜索得出裁剪结论。

标准版验证原有核心操作与数据兼容；独立定制版另验证并行安装、CLI、数据和更新隔离。保存构建信息与验收结果，不预设包体积或内存收益；分别测量并记录变化。

## 待评审项与依据

推荐先确认最小公共壳、首个交付所需特性集合及第一项真实定制功能；未明确的产品身份保持占位，不阻塞以现有 Herdr 验证裁剪机制。本草案不创建已接受 ADR，实施前对多产品数据身份与公共兼容性形成决策记录。

- [Cargo features](https://doc.rust-lang.org/cargo/reference/features.html)：条件编译、可选依赖、默认特性及特性合并。
- [Cargo profiles](https://doc.rust-lang.org/cargo/reference/profiles.html)：编译优化与调试配置，与产品组合分开。
- [Cargo workspaces](https://doc.rust-lang.org/cargo/reference/workspaces.html)：多 crate 的统一管理。
- [Tauri 插件](https://v2.tauri.app/develop/plugins/)：可独立装配的命令、状态和初始化。
- [ADR-0008](../adr/0008-primary-application.md)：当前单主应用与公共实现约束；本草案尚未改变现状。

## 首期命名与目录补充

根据实施确认，公开验证配置命名为 `personal`（个人版），不使用以“排除某功能”为名的产品标识。`standard` 缺省保留全部现有能力。`personal` 首期排除 Herdr，产品名称不限制后续可选特性集合。

产品编译、开发与安装统一经 `agent-hub.sh`／`.bat` 的共享 Node 入口。独立产品的 Cargo 目录与标准 `target` 同级，避免标准清理递归影响其他产品；前端、CLI、sidecar、安装身份及用户数据均独立。新增构建工具和装配 interface 按目录结构文档集中归属。
