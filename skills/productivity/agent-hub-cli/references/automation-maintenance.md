# 自动化巡检与迭代

适用：用户要求巡检定时任务、修复任务故障，或建立持续改进任务。本文是 Agent
操作流程，不表示 CLI 自带巡检、自愈、目标路由或业务授权引擎。普通任务编辑
沿[创建与运行规范](automations.md)，不必新增监督任务或长期 Agent。

## 范围与目标

先解析匹配 CLI，读取当前帮助。具体目标以 `show` 的真实 ID、definition、
revision、工作目录、依赖与运行状态为准；名称仅用于发现，重名必须消歧。
不要把当前项目、已有平台登录或历史路径当作目标任务的绑定。

用户要求建立通用巡检时，默认方案可命名“定时任务巡检”；经授权覆盖
`automations list` 返回的受管任务。只检查指定对象时用“指定任务巡检”，
从明确 ID 或经唯一解析的名称定位，再按定义选择适用 Skill 和业务验收。
专项方案可以描述 MR、Issue、备份等业务，但不能把某一业务的平台、间隔、
终态或恢复次数推广到其他任务。已有专项任务不能未经授权扩成全量维护。

全量巡检先形成目标清单，逐项做基本检查；按风险与待验证修复排序，耗时操作
设本轮预算，未覆盖项和未完成修复明确记录并优先续办，不能宣称已覆盖全部。
排除自身及其他巡检/监督任务的递归修改，除非用户另行指定维护对象；外部只读
任务不写入。暂停和仅手动任务保留原意图，不因未定时执行判错或自动启用。
需要自动化持续运行时使用真实调度器，不以当前会话循环等待代替任务。

## 每轮证据

以 JSON 读取目标 `show`、最近 `runs`、相关 `logs --run` 和必要业务状态。
大定义和日志先解析再输出摘要；输出截断或缺字段时补读准确 run/文件，不能
当作“没有错误”。按目标自身日程、时区、执行互斥、运行时长和宿主能力判断
是否漏调度；`next_run: null` 本身不证明故障。

分别核实以下层次，记录来源时间和准确版本：

| 层次 | 有效证据 | 不能单独证明 |
| --- | --- | --- |
| 调度 | 启用状态、近期运行序列、必要的原生注册只读结果 | 下次时间为空、配置已保存 |
| 执行 | 控制器/Worker 阶段、原进程/会话身份、送达及回调回执 | working、派发成功、退出码 0 |
| 进展 | 新业务输入/产物版本、真实 Job/验证阶段变化、已确认成果 | 屏幕刷新、重试次数增加、重复评论 |
| 验收 | 当前版本的独立评审、适用验证/平台门禁、实际业务终态 | 旧版本成功、作者自查、状态标签 |
| 收尾 | 原任务的资源归属、停写/成果保全与释放回调 | 业务结束后面板空闲 |

控制器失败、Worker失败、送达不明、业务回调缺失、写入未决和平台阻塞分别保存
原因。最近的运行不能掩盖先前未收齐的回执。旧来源的评审、CI与队列结果保留
审计，不签发新来源通过；pending 先核实原评审是否运行，不重复创建评审。

## 原所有者与恢复

维护者只修复自动化机制，业务仍由原任务和原 Agent 编排。原 Agent 有真实
进展时只观察；进度长期不明时沿原任务已支持的状态/恢复入口核验，不能因
working 永久跳过诊断，也不能因超时另发业务提示词或启动替代 Agent。

无进展窗口由任务配置和业务性质决定，不写死通用两小时或十分钟。分别记录
本地 Agent 活动与远端业务进展；重试、回调、升级和目标正常前进不能随意清零
停滞时钟。恢复前收回准确执行、租约及未决写入；恢复提示应由原任务携带当前
来源版本、最新有效问题与验证链证据，不能只带粗略动作而继续处理过期输入。
已请求/送达不明的恢复先读回，不重复发送；既有恢复回执不因版本升级失效。

“需人工”“待作者”“方案确认”是需解释的状态，不是通用终态。核实原始问题
属于技术判断、修复要求、正式审批还是外部缺口：已有有效代理授权覆盖的技术
选择与可恢复故障，由原任务消费授权继续；没有授权不能推定同意，代理决定
也不等于独立评审通过。正式审批还需真实身份权限与平台规则允许。

权限、凭据、必要输入或外部资源确实缺失时，保留最小待办、已核实责任归属、
解除条件与下轮检查点，继续不依赖缺口的工作并复查；不要向第三方发消息或
索取令牌。额度耗尽先核实已有持久恢复窗口，不能自动加额、清零次数、删除
人工状态、降低严重性、清除问题或绕过门禁制造进展。

## 有证据的最小迭代

1. 区分任务机制缺陷和业务尚未完成。记录触发条件、准确运行/版本、预期与
   实际结果；正常进展没有缺陷时不改文件、不重跑、不清理。
2. 从最新 `show.definition` 构造临时隔离副本，复现失败。任务逻辑测试使用
   假平台、假 Agent 和临时状态，不连接生产写入；需要隔离 CLI 数据时使用
   新的绝对 `AGENT_HUB_AUTOMATION_HOME`，`--skills-root` 不隔离自动化。
3. 只修复所证实的脚本、提示词或恢复配置缺口，按变更选回归；代码缺陷必须
   有失败回归转绿，纯文案变更检查契约、引用与方案一致性，不伪造红绿证据。
   覆盖新输入、重复送达、旧回调、未决写入及正常进展不重复派发等相关边界。
4. 按 SemVer 升级任务内容版本，检查 UTF-8 包预算；用最新完整 definition 和
   同次 revision 保存。发生并发变更先比较合并，不能只换 revision 覆盖。
   保留全部 files、依赖、绑定和运行策略，不手改回执、状态库或调度器。
5. 保存后读回原 ID、版本、完整定义、日程和启用状态。保存失败保留旧任务，
   先解决具体校验问题，不连试不同写入猜测结果。CLI 缺能力时说明未完成项，
   不用复制/重建实例替代原地升级。
6. 优先观察原调度；确需验证且任务已授权运行时最多触发一次。原执行活跃、
   送达/写入不明时只读核验，不重复触发。离线通过、保存通过、生产恢复和
   业务终态分开报告；未看到实际恢复标记待验证，下轮优先检查，不宣称已修好。

任务升级不修改日程、启停、额度、计数或租约来掩盖失败。共享生命周期和状态
存储缺陷属于产品/公共模块边界，明确指出缺口；没有项目修改授权时不把临时
复制的执行器或存储实现塞入每个任务。

## 记录与交付

每轮在维护任务的原生运行记录中留覆盖清单、证据、根因、修复、回归、读回、
生产验证、未决与下一检查条件。必要跨轮信息仅存维护任务自己的
`.local/state/task-state.json` 的命名扩展，按目标 ID 分区，使用 CLI 解析的共享
`TaskState.extension(namespace)` 锁与原子更新；保留已有扩展名和历史，不因
任务改名或方案切换迁出第二份权威状态。目标任务的业务状态仍归原任务。

`files`、导出、备份和提交不包含本地状态或运行日志。示例使用保留域名和占位
路径，不记录真实账户、令牌或不必要的原始认证输出。最终报告实际检查范围、
已修复及已验证项、尚未恢复或尚未验证项；不能用“已配置自进化”替代运行证据。
